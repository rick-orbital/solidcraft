# CAD persistence v1: initial contract

Status: implementation contract for Gate 1, subject to repository schema conventions. Principal and schema/subgraph access are resolved server-side for every operation. Client-supplied workspace or design IDs never grant access. A design is bound immutably to an authorized workspace schema and canonical subgraph; initial writes require the existing subgraph WRITE grant. A read grant does not grant a lease or write.

All IDs are opaque. Counters and fences are monotonic nonnegative integers encoded as decimal strings at JSON boundaries. Timestamps are server-generated. Native bytes are bounded before buffering, SHA-256 validated, and stored under immutable unique keys; the service never trusts a client hash without verifying bytes. A revision records design, parent/base revision, immutable object key, hash, size, generation, engine build and creation metadata. The accepted head is the only authority for Saved. The design and revision APIs expose only data the principal can read.

A design has at most one editing lease. Acquire and explicit takeover atomically advance a persisted fencing counter; renew checks the same lease and fence and server-side expiry. Expired, revoked, wrong-principal or superseded leases cannot commit. Default lifetime 60 seconds and heartbeat 15 seconds are configurable. A takeover invalidates the old lease and must not discard the old client's local unsaved work.

A commit supplies design ID, lease ID, fence, expected base revision (or explicit empty head), session epoch, generation, idempotency key, hash, size and bytes. Blob durability must be established before acknowledgement. In one database transaction, verify permission binding and live lease/fence, check idempotency and exact base, create the immutable revision and advance the head. Two commits against the same head cannot both succeed. The same idempotency key with identical request returns the same accepted revision; reuse with different content or context fails. Orphaned uploaded blobs are permitted on rejected commit but must be cleanup-safe. No successful save is returned before accepted revision metadata and durable bytes exist.

If workspace publication lies outside that transaction, insert a durable outbox item in the same transaction and retry publication idempotently. A failed publication does not roll back or hide the accepted revision; publication status must be visible. Define object-store durability and recovery domain explicitly. Persist operation IDs and states for later relay reconciliation; do not make process memory authoritative.

Errors are structured and bounded: unauthorized/not found, read-only, lease held, expired/revoked lease, stale fence, base conflict, invalid/oversize content, idempotency conflict, storage unavailable, and outcome unknown. Avoid revealing unauthorized design existence. Expected conflicts are recoverable results, not infrastructure alerts.

Initial operation transition authority: the relay/service records `queued -> running -> applied -> verified -> saving -> succeeded`; only a durable accepted revision permits `succeeded`. Before dispatch a rejected operation may become `failed`; once delivery or application is uncertain, record `outcome_unknown`, block subsequent mutations for that session and reconcile from persistent operation and revision evidence. Never automatically replay an uncertain command. A failed restoration freezes editing and exposes recovery. A new session epoch invalidates old queued work.

Gate 1 verification uses real Neo4j and object storage semantics, not just mocks: unauthorized/read-only write denial, two competing head commits with exactly one winner, expiry/revocation fencing, lost-ack retry returning the same revision, and durable publication retry after failure. Include transaction interruption and idempotency conflict. The editor bridge and generic Neo4j OCC tests alone cannot establish these results. No live agent mutation is enabled by this package.
